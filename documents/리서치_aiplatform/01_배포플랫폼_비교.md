# 배포 플랫폼 비교 — simploy vs AI Platform

## 목적
누끼(BiRefNet) Python API 서버를 사내 인프라에 가볍게 올리기 위한 플랫폼 선정.

## 비교표

| 항목 | simploy (EC2 dockerCompose) | AI Platform (BentoML) |
|---|---|---|
| 대상 | 범용 웹 서비스 | ML/AI 서빙 전용 |
| 언어 | 모든 언어 (JVM 외는 dockerCompose) | Python 전용 |
| GPU | 표준 AMI에 없음 → Launch Template 커스텀 협의 필요 | 기본 지원 (A100, A40 등) |
| 초기 셋업 | CMDB Service/Role/Zone 신청 → 배포 스택(ALB/ASG/TG) 생성 → Jenkinsfile 작성 | copier 템플릿으로 프로젝트 초기화 → `#support-aiplatform` 워크플로우 |
| 인프라 관리 | 본인 담당 | 플랫폼이 관리 |
| 모니터링 | 직접 구성 | Langfuse, Prometheus, Grafana 자동 |
| 스케일링 | ASG 설정 | 자동 스케일링 + 시간대 스케줄링 |
| 적합한 경우 | 일반 웹 API, 중소규모 트래픽 | ML 모델 서빙, LLM, 데이터 처리 API |

## 심플로이에서 Python을 올리는 방법 (참고)
- 웹 배포 타입: `springBoot`, `springBootWeb`, `dockerCompose` 중 **dockerCompose** 사용
- 컨테이너 이미지는 사내 레지스트리 `wcr.baemin.in`에 푸시
- dockerCompose 설정에서 `image`, `ports`, `environment`, `healthCheck(/health)` 지정
- JVM 외 언어(Python, Node, Go)에 권장되는 타입

## 선택 근거
1. **용도가 정확히 ML 추론** (BiRefNet 누끼)
2. GPU 필요 → simploy는 별도 협의, AI Platform은 기본 지원
3. "가볍게" 목적 → CMDB/배포 스택 구성 작업이 없는 AI Platform이 맞음
4. 운영 부담 최소화 → 플랫폼이 모니터링/스케일링 처리

## 결론
→ **AI Platform으로 진행**
